Retry with backoff in fetch_page

TL;DR: fetch_page now retries HTTP 429 and 503 up to four attempts with exponential backoff, and honors Retry-After up to an 8 second cap. Other failures still raise immediately, and FetchError now reports how many attempts were made. Tests pin the wait sequence by injecting a fake sleep.

Assumption: the target is commit 39f902e on branch retry-backoff compared with main (ff3253d). This is a small invented sample repository used for the demo. I ran its 6 tests and all passed.

Background

fetch_page(url, session) sends one HTTP GET through a session object and returns the body on status 200. Before this change, any other status raised FetchError immediately.

HTTP 429 means the server is rate limiting the caller. HTTP 503 means it is temporarily unavailable. Both usually clear within seconds. A server can send a Retry-After header to say how long to wait.

Mental model. A session is any object with get(url) that returns something with status, body, and headers. Tests use a small fake, so no network is involved.

1. Decide what counts as transient

names the two statuses worth retrying. adds an attempts field to FetchError so callers can log how hard the function tried. It defaults to 1, which keeps existing FetchError(message) calls valid.

2. Compute the wait

returns Retry-After when the server supplies it, limited to max_delay. Otherwise the wait doubles from 0.5s and stops growing at 8s. attempt counts from 1, so the first wait equals base.

3. The retry loop

returns on 200 and raises immediately for statuses outside RETRYABLE. On the final attempt it raises instead of sleeping, so no time is wasted after the last failure. Otherwise it sleeps and tries again. sleep is an argument, defaulting to time.sleep.

4. Tests pin the waits

and pass waits.append as sleep, so they assert the exact wait sequence without delaying the run.

Edge case not covered. Retry-After may also be an HTTP date. The loop calls float() on the header, and float("Wed, 21 Oct 2026 07:28:00 GMT") raises ValueError when run. This is observed behavior of the code, not a stated goal of the change.
